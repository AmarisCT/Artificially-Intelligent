# Security and moderation report

Scope: the Research Commons as built on branch `feature/research-commons`, and the controls the not-yet-built receiving service and moderation inbox must provide. Honest summary first.

**What is protected today:** the live site cannot receive, store or publish a visitor's text through the Commons, because no submission endpoint exists and every form is switched off. The page is static; it stores nothing a visitor types; it has no credentials, no moderation controls and no private data.

**What is not protected, because it does not exist:** the submission service and the moderation inbox. Their security rests on whoever builds them following [CONTRACT.md](CONTRACT.md) and [ARCHITECT-MODERATION-SPEC.md](ARCHITECT-MODERATION-SPEC.md), and passing the conformance cases. Nothing in this repository can enforce that. Do not describe the Commons as "secure" in public until the service has been built, tested against the conformance cases and reviewed.

| 10 | **Contributions treated as evidence** | Visitor text is labelled everywhere; it is never in the Inquiry Engine's starting map or guided answer; a relationship is shown as editorial, automated suggestion or preliminary; the Observatory path treats a recommended paper as a candidate for review only | Search, Inquiry Engine, constellation | `test_shared.py` (7), UI constellation tests | A reader may still over-trust a label; wording is deliberately plain |
| 11 | **Cross-site request / CORS abuse** | Exact-origin CORS (never `*`), JSON only, no cookies (`credentials: "omit"`), `Origin` checked server-side | Service | `test_cors_is_not_treated_as_security`, conformance | CORS is not authentication; it only limits browsers. ## Moderation controls (design, to be built)

- **Every contribution is read by a person before it is public.** There is no auto-approve, no trust score and no allow-list that skips review.
- **Four automatic signals only flag, never decide:** possible personal data, possible threat or doxxing, promotional language, similarity to an existing public item or recent submission. They sort the editor's queue; they never approve, decline or publish.
- **Decisions are recorded, reasons are private.** A decline reason is an internal note and is never published, and a decline is not shown to anyone but staff.
- **Editor accountability** is an internal audit trail (who, when, which transition, hash of the approved text). Moderators are not named publicly.
- **Corrections are public, simple and fast:** withdrawal removes the text, the page, the search entry and the constellation node at the next build, and leaves a short dated tombstone.
- **Appeals and takedown:** a contributor or a third party can ask for withdrawal or correction. The route is an owner decision (a dedicated address, or a form, which would itself need to be built); see [APPROVALS.md](APPROVALS.md).

## Things I could not verify

- I could not reach the live site, the Architect backend, Search Console or GitHub Pages settings from my workspace, so nothing was tested against production.
- I have not performed a penetration test, and the reference implementation is Python, not the production stack. Treat the conformance cases as a minimum.
- Legal questions (licence, defamation exposure, takedown obligations, children's privacy, jurisdiction) need the owner's decision and, ideally, a lawyer. I have drafted nothing as legal advice.
